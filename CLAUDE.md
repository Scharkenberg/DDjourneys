# DDjourneys: context for Claude

Journey planner for DVB/VVO (Dresden), .NET 11 MAUI / C# 15. Repo: `Scharkenberg/DDjourneys`. Owner commits and pushes himself. Models after the Android app oeffi, but modern. Departures live in the separate repo DDepartures. Always fetch the latest repo state first; he edits code between sessions. Discard remembered code that the repo contradicts.

## Working rules
- Terse. Deliver final code per step, no elaboration. Complex points get one simple explanation. Prefer current docs; never rely on superseded information.
- Do NOT compile MAUI code or shim MAUI types in the container. Verify against the official Microsoft docs (Microsoft Learn MCP) instead. Core (net, no MAUI) may be unit-checked.
- Generated files use CRLF and tabs. Deliver changed files as a zip with repo-relative paths (SendUserFile); when asked for "just the fix", print only the code.
- JSON is source-generated, never reflected: `JsonSerializerIsReflectionEnabledByDefault=false`. Provider DTOs go through `VvoJsonContext` (add a `[JsonSerializable]` for every new DTO root); wire objects without a DTO are `JsonObject` trees (`Wire.Array`, no anonymous types, they are trimmed away on Android); stored lists are written with `StoredJson.Write(items, toNode)`. `ExpertReport` reads DTOs through `VvoJson.TypeInfo`. No `yield` inside catch; regexes are `[GeneratedRegex]` (SYSLIB1045; the class and its outer types are `partial`).
- Analyzer baseline (C# 15): collection expressions everywhere (`[]`, `[.. x]`), field-backed `get;`, primary constructors, `Lock`, null-conditional assignment, UTF-8 literals, `CancellationToken` always last (CA1068; positional ct-only calls become `cancellationToken:`), `FirstOrDefault()` on lists as `Count > 0 ? x[0] : null` (CA1826), types that implement WinRT interfaces are `partial` (CsWinRT1028). In the app project a collection expression that targets `IReadOnlyList`/`IEnumerable` is cast to a concrete type (`(List<T>)[.. x]`, CsWinRT1032). XAML-bound constants are `const` with `{x:Static}`, localized text uses `{localization:Tr}` (no instance property just to read a static).
- Dependencies: CommunityToolkit.Maui, plus MAUI's own `Microsoft.Maui.Controls.Foldable` (`$(MauiVersion)`, `UseFoldable()`). Own ObservableObject/AsyncCommand, built-in DI and Shell.
- Verify before finishing: brace balance, XAML well-formedness, every `{localization:Tr Group.Key}` exists, usings, no leftovers.

## Wide windows (panes)
- Plan, Results, Journey, Map, Departures, Run and Vehicles derive from `Support/PanePage` (XAML root `support:PanePage`). Panes: one per `PaneRules.MinPaneWidth` (360 dp; 720 = two, 1080 = three ...; `Hysteresis` 40; at most `MaxPanes` 5). With room for two or more, the current Shell page is the host: a page opened from it that pairs (`PaneRules`: Plan>Results, Results>Journey, Journey>Map/Vehicles, Departures>Run, Run>Map/Vehicles) is lent to it, not pushed. The host shows the deepest pages of its chain that fit; each step shifts the chain one column left; a resize shows more or fewer of the same chain. Narrow windows keep the plain Shell stack.
- Back always closes the deepest pane first, in every path: Android back and predictive back gesture (`Platforms/Android/PaneBackCallback`, an AndroidX `OnBackPressedCallback` enabled while `Panes.CanGoBack`, following `Panes.BackChanged`), the Shell title-bar back (`BackButtonBehavior`), `Page.OnBackButtonPressed`, and the panes' own back arrow (left-most visible pane, whenever the host's title bar offers no back: start page, or host content hidden) and close button (deepest pane). `Panes.GoBack()` is the one entry point.
- Pane motion (`PanePage.Animate`): one `Animation` drives all panes (FLIP: old on-screen x minus the exact new cell x from `PaneFrame.LeftOf`, set in the same pass as the cell); a new arrangement takes over from a running one; `Motion.QuietEntrances` mutes card entrances meanwhile. `PaneFrame` replaces grid definitions only when the shape changes and sets a cell only when it differs.
- Default font: System (`FontCatalog.SystemId`); a stored choice is kept.
- Lent pages are full pages created through DI and never pushed: `Panes` applies the query to page and view model like Shell, moves the page's content into a `PaneSlot` (header with title, toolbar items, close) and drives `OnAppearing/OnDisappearing` itself. Width changes replace the pages by new instances on the same view models (`PaneRules.Recreate`, `Panes.GatherAsync/SpreadAsync`; state outside the view model goes through `RecreationQuery`, e.g. the map scene; `OnRetired` releases the old page's subscriptions). A view with native views is never moved to another page: the page's own content sits in the frame from construction (`PanePage.SetFrame`). Back to the start: `Panes.ToStartAsync(shell)` (closes all panes) instead of `GoToAsync("//plan")`.
- Rules for these pages: navigate with `Panes.GoToAsync(route, parameters, from)` (`from` = the page or view model asking; without it the call is a Shell push) and `MapScenes.OpenAsync(scene, title, from)`; call `LeaveIfGone(args)` in `OnNavigatedFrom` instead of `PageTeardown`; dialogs through the page's own `DisplayAlertAsync/DisplayActionSheetAsync` (redirected to the host while lent), popups on `DialogPage`. A new pair is one line in `PaneRules` plus the `from` argument at the call site. Log lines `[Panes]`.
- Foldables: the frame (`Support/PaneFrame`) is MAUI's `TwoPaneView` (`UseFoldable()`), configured to split only across a fold; its own row/column sizes after measure give the fold position inside the frame (`FoldLayout`). Its two pane containers stay empty (a view moved between them would change parent); all panes live in one grid (`PaneFrame.Strip`) spanning the frame and only change cell. Vertical fold: panes split between both sides (each side as many as fit, at least one, deepest on the far side, nothing on the hinge); on a tri-fold MAUI reports one fold, and the two-section side gets two equal columns, whose border is the other fold. Horizontal fold (tabletop), only where the width already splits: the deepest pane above, the others in columns below. MAUI counts a flat foldable as spanned (ignores `isSeparating`).
- Never move a view that already has native views into another parent (Windows breaks: stale measures, empty content, flicker). Build structure before the handler exists (`PanePage.SetFrame`, `PointerLight` installs its overlay on `HandlerChanging`, `StopNameView.SingleLine` set from XAML); panes only change their cell in `PaneFrame.Strip`.

## TRIAS (VDV 431-2, schema v1.4, checked against github.com/VDVde/TRIAS)
- A `Service` keeps its line data in `ServiceSection` (LineRef, DirectionRef, Mode/PtMode, PublishedLineName, OperatorRef); `TriasMapper.Properties` reads the first section, or the service itself for older flat responses. Destination, JourneyRef, Attribute and the status flags stay on the service.
- Journey stops are identified by stop place (`StationId`: first three DHID parts), the platform is a detail. Changes are `InterchangeLeg` (`InterchangeMode`: walk, protectedConnection, guaranteedConnection, remainInVehicle; `WalkDuration`, `BufferTime`) or `ContinuousLeg`; only the connection modes are guaranteed.
- Versions: every request is written for 1.4 and steps down 1.3, 1.2, 1.1 (`TriasClient.SendAsync(kind, build(dialect))`, `TriasDialect`). Rejected = non-transient HTTP error, unreadable XML, or an `ErrorMessage` without any result and not a "no result" code. The working version is remembered per `TriasRequestKind` and 1.4 is retried after 30 min. Unreachable/timeouts never downgrade. Each attempt is logged (`[TRIAS] ...`). Only 1.4 is in VDVde/TRIAS; which optional parameters older versions know (`HasExtendedContent` from 1.3, `HasMobilityAdditions` 1.4) is an assumption.
- Request parameters are an XSD sequence: keep `TriasRequests` in the order of `TripParam`/`StopEventParam`/`TripInfoParam` (1.4: `InterchangeLimit`, not `TransferLimit`; it is a positive integer, so "no transfers" is filtered client-side).
- TripInfo (`TriasRequests.TripInfo`, `TriasMapper.MapRun` → `RunDetail`) refreshes a run from `JourneyRef` + `OperatingDayRef` kept in `TriasRunData`; falls back to the stop event's calls. `IDepartureProvider.GetRunDetailAsync` (default: stops only) carries `RunDetail.Vehicle` (`CurrentPosition`) and `OperatingDays`; the Run page shows operating days and `MapScenes.FromRun` adds a reported-position vehicle marker (and then prefers the static map over the live lookup).
- `FaresParam` (`PassengerCategory`, last element of `TripParam`) is sent from 1.4 on for non-adult passengers (`RoutingPreferences.Passenger`, option "Tickets for" on the routing page, per provider). `IncludeOperatingDays` from 1.3; `OperatingDays` (From/To/Pattern bit string, description) → `JourneyLeg.OperatingDays`, shown on the leg as "Runs Mon–Fri" (`OperatingDaysText`, nothing when daily).
- Situations: `Situations/PtSituation` (SIRI SX: SituationNumber, Summary/Description/Detail) are matched to `SituationFullRef` on the trip and its legs and become `Journey.Notices` / `JourneyLeg.Notices`. Call-level `Occupancy` fills `RunStop.Occupancy`.
- Not implemented: `CurrentPosition` on journey maps (only the run map), traveller age/owned tickets in `FaresParam`, Trias_Booking/Facilities/Alerts.

## Journey page actions, followed journeys, input mode
- Icons for maps: `MapPin` = live tracking of one vehicle or trip (leg button on the journey page, run page, followed journeys); `Map` = a map that does not follow one vehicle (journey overview, stop surroundings, pick on map). The leg action row (`LegRow.HasActions`) is pin + "Earlier" + "Later" (short words, long hints as accessibility descriptions).
- Earlier/Later on a ride (`JourneyService.GetLegAlternativeAsync`): the provider's own continuation (VVO `tr/prevnextmove`) is asked first and its answer counts only if the ride really moved to the wanted side (`LegAlternatives.Pick`: same line and stop, planned departure moved by more than 30 s); a provider that answers with the same ride, nothing, or fails falls through to `LegAlternatives.ComposeAsync`, which works for every provider: direct connections between the two stops of the ride (`MaxTransfers.None`, no alternative stops) are searched, the nearest earlier/later one (same line first) replaces the ride, and when it no longer connects with the leg after (later) or before (earlier) that part is planned again (`JourneySplice`: legs + transfers re-indexed, flags of the old pair reset). A composed journey has no session (`Id`/`Context` null: no PDF, no provider continuation), so the buttons (`JourneyViewModel.HasLegAlternatives`) depend only on the journey having a ride. Log lines `[Leg alternative]`. The view model never loads the same journey again (no-op answers were the "RAM grows per click" symptom) and shows `Journey.LegSearching` while it works.
- Via (`ViaRouting`, applied by `JourneyService.SearchAsync` to every provider): the provider is asked with the stop-over, only journeys that really pass it (`ViaRouting.Passes`: stop of a ride, transfer, same name or within 120 m) are kept; none (provider ignores it, refuses it for address/POI endpoints, fails) -> two ordinary searches (start -> via, via -> destination, fitted by time, 1 min stay) are joined. Earlier/later pages of a via search are windows of that search (no native continuation). Log lines `[Via]`.
- Timeline rhythm (`JourneyPage.xaml`): text column padding top 4, bottom 12 (intermediates 8), spacing 4 (leg column 6); the notice card margin 4,12.
- Settings must do what they say: a control that the selected provider ignores is hidden (`ProviderCapabilities`: `WalkToStops`, `SupplementFilter`, `RouteOptimisation`, `PassengerFares`; `RoutingSettingsViewModel.Show*`), a setting that only applies somewhere says where in its text (occupancy and platforms: "in journey details"). `AppSettings.TimeoutSeconds` sets `ApiClient.DefaultTimeout`, so it holds for every call that names no timeout.
- About page: the README (repo root) is an `EmbeddedResource` (`DDjourneys.README.md`), and `LIESMICH.md` its German twin (`DDjourneys.LIESMICH.md`); `AboutPage.ResourceFor(language)` picks German for "de*", else English. Read by `AboutPage` and shown by `MarkdownView` (native controls) via `Core/Documents/MarkdownDocument`. The READMEs are for laypeople: prose with headings, no lists, no bold, no quotes (tests enforce it). Both files must always be kept in sync: every change to one is made to the other in the same step (`ReadmeLanguagesTests`: same sequence of headings and paragraphs, same links and code spans).
- Performance rules: `ApiClient.CreateHandler()` (SocketsHttpHandler, gzip/deflate/brotli, pooled connections) is the one handler; every `RelativeSource` binding carries `x:DataType`; looping animations (`Motion.Breathe`, `Skeleton`) wait for `Motion.WaitUntilWorthAnimatingAsync` and run only on the page the user sees (`Motion.IsShowing`); Android shortcuts are published only when labels or build changed.
- Journey page actions are icons in the overview card (`JourneyActions` in `JourneyCardModel.Actions`, left of the map icon): PDF, hand-over to another app, follow (bell, solid when followed; a tap toggles), pause/resume (only while followed), and the notice badge (warning icon + count, scrolls to the notices; on result cards it is a plain badge). A followed journey shows one slim tappable strip (opens the followed journeys). `IconButton.TargetSize` (44 default) lets rows of several icons use 38-40.
- Walks at both ends of a followed journey: the service follows vehicles only, so `FollowedWalks` (Support, written in `SchutzengelJourneyTracker.FollowAsync`, dropped with the journey) keeps the leading and trailing walk (transfers before the first / after the last ride, plus walking legs there) and `TripTimeline.SetWalks` adds them as footpath episodes with real-time-shifted times. The journey therefore starts when the walking starts and ends at the destination; the live content says "Walk to X" + "From t1 until t2" (`NotifWalkFromUntil`), `TripSnapshot.IsFinalWalk` marks the last walk.
- Followed journeys never vanish from one bad answer (`SchutzengelJourneyTracker.SyncPlanListAsync`): a plan missing from `plansMinimal` is asked for directly (`IsGoneAsync`, `planRawData`; only "no such plan" counts), then needs 3 lists in a row and 10 min since it was last listed; a plan is hidden as "replaced" only by ANOTHER plan naming its trip; a missing token never clears the cache; a 401 is repeated once with the same token before the account is replaced (a new account loses every plan).
- Followed journeys page (`TrackedJourneysViewModel`): fetch interval 20 s while a journey is under way, 45 s when one starts within 90 min, 3 min otherwise, 15 s after an error; between fetches the rows follow the clock every 10 s (`Reconcile`: planned becomes under way, past arrival becomes arrived, progress moves on from the last answer); the next answer replaces it all.
- Input mode (Settings > Start, `StartSettingsPage`): `AppSettings.StartInput`, `StartFrom` (device position or a chosen place), `StartFromPlace` (per provider; picked through the place search with `Routes.TargetStart`, any stop, address or POI, not added to the recents). Once per start the planner fills the start and opens the destination search (`PlanViewModel.StartInputModeAsync`); a pending contract request or quick action wins (`ContractEntry.HasPending`, `AppShortcuts.IsBusy`).
- The departures page pins the stop line and the departures/arrivals/now row; the planner's From/To/Via cards use 38 dp icon targets and 50 dp rows.

## Fares
- `JourneyFare` (kind, price, zones, notes, valid-for, url). VVO: `VvoFareMapper` turns the route's `Price`/`PriceDayTicket` (+ zone names, `TicketNotes`) into a single and a day ticket; the API quotes nothing else. TRIAS 1.4: `TripFares/Ticket`. `FareChoice.Preferred(fares, passenger)` picks the one ticket cards, header and shares name: the passenger's own single ticket, else tickets without a passenger statement (VVO quotes only the normal price), else adult. The journey page section is collapsed by default (header: preferred ticket and price; expanded: compact rows, zones and conditions once).
- A change is "endangered" only by arithmetic once real-time times exist on either side (`TimelineBuilder.CreateBoundary`); the provider's flag counts only without real-time data.

## Interfaces, versions and diagnostics
- `InterfaceSchemas` (Core) is the versioned list of every interface the app depends on: external services (VVO WebAPI, TRIAS, Schutzengel, TLMS, open data Dresden, CARTO), internal formats (stored lists, map bridge, widget data, preferences storage) and the contract. Official versions (TRIAS 1.4, contract 1) are used as they are; for services without a published version the app keeps its own revision `rN` in `InterfaceSchemas.Revision`: raise it whenever a DTO, a mapping rule or a stored/wire format changes. Endpoints live there as constants (`VvoWebApiUrl` ...) and the clients use them. `AppInterfaces` (app) adds the storage schema, `Report()` is shown under Settings > Developer options > Interface versions (copyable) and is written at the top of the log (`DiagnosticLog.StartInfo`). New external API, stored format or contract change = update the list and the tests.
- Contract requests are logged as `[Contract vN] ...` (accepted, refused with code, dropped as double delivery).
- `StartupGuard`: `Begin()` first in `MauiProgram`, `Complete()` 3 s after the first navigation. Two unfinished starts in a row make a safe start (saved window position forgotten, quick-action publishing skipped, tracking resume delayed 20 s). Keep first-screen work minimal; defer the rest.

## VVO API facts
- A partial route with `Mot.Type == "Footpath"` is a transfer without stops; `StayForConnection` is an ensured connection (shown as a message, not a real change); `Mobility*` is accessibility.
- Walk-only trips have only transfers, so the mapper builds a synthetic `TransitMode.Walk` leg (`VvoJourneyMapper.WalkOnly`).
- `Journey.Origin/Destination` come from the searched Location (centre point); `leg.From/To` carry platform-level coordinates (GK4→WGS84). Map start/end markers use `MapScenes.Terminal` to prefer the leg position when it is the same stop.
- Timeline: `TimelineBuilder` yields Ride/Walk/Boundary items; `TimelineRows` renders them. An interchange node is merged only when both legs use the same stop (`SameStation`). A change that walks to another stop renders alight → walk → board.

## Maps and web views
- Two map engines in one `HybridWebView` page (`wwwroot/index.html`), chosen in Settings > Map (`AppSettings.MapEngine`, `MapAvailability.Engine`, preference `mapEngine` = `carto`|`leaflet`): `carto` = MapLibre GL JS 5.24.0 (vector, WebGL 2), `leaflet` = Leaflet 1.9.4 (`wwwroot/leaflet/`; any web view; 1.x on purpose, 2.x is ES-module only). Leaflet tiles: `tileSources` in the page, tried in order: OpenStreetMap `tile.openstreetmap.org` (no key; light only, dark mode inverts the tile pane by CSS; the choice of DVB-Fahrplan and other Leaflet apps) then CARTO raster `rastertiles/voyager`/`dark_all` (with `?key=` if set). A source that delivers no tile after 4 errors is dropped for the next (`[Map page] tiles: ...` in the log). The first version used CARTO raster alone and showed no base map: CARTO now wants its key there too. Keep a tile policy in mind (OSM usage policy: light use, attribution). The page has an `engines` table (marker, jump, ease, fit, theme) behind the shared scene code (markers, popups, route lines with casing/dashes, fit, Auto-fit, explore/pick, view reporting, controls); keep both in step when a feature is added. Controls: zoom and fit-now top right, attribution (collapsed "i") bottom right, Auto-fit bottom left (the top is covered by the page's hints). Startup: the page says `boot`, `MapView` answers `ddBoot('start', {engine, force})`, the page loads the chosen library and runs `ddMain(engine)`, then `ready`. `ddMapCall(command,json)`: init/theme/set/focus/overlay/mode/center/key. Raw messages: `boot`, `ready`, `unsupported:`, `open:`, `error:`, `auto:true|false`. Changing the engine replaces the web view (`MapView.ApplyAvailability` creates a fresh one per start). CARTO vector styles need the user's own API key (Settings > Map, `AppSettings.MapApiKey`, `MapAvailability`); the app ships none. Without a key, or when CARTO answers 401/403 (`keyrejected`), `MapView` shows a calm notice with a button to Settings instead of the map, and `MapPage` does not locate or load stops. Exactly one attribution control (collapsed "i"). A 32 px free strip sits under the map so swiping off the map is always possible. Option "Auto-fit" (persisted `Preferences` key `MapAutoFit`); manual pan/zoom switches it off for the session.
- Android build: `UseMaterial3` is true in the project file (Material 3 handlers for Entry, pickers, sliders; MAUI docs: only Android is affected, our own styles still override defaults).
- Following a journey leg starts with `LegRunResolver` (Core): the departure at the boarding stop that is this leg (same line, scheduled time ±90 s, destination as tie-break) is looked up through the departure monitor and its whole run (stops before and after the boarding stop, any provider) is the course, because the passenger usually looks before the vehicle has reached the stop. Fallback below.
- Following a journey leg (`TrackTargets.FromLeg`): stops with positions and times, else the leg geometry with times spread by distance (TRIAS calls carry no coordinates; `TriasProvider` also looks stop positions up for runs). A leg with neither opens nothing (the live page would show every vehicle of the line). "In progress" is evaluated against the clock (`LegRow.IsActive`, page timer).
- Tracking mode: `Routes.Track` carries a `TrackTarget`; only the matched run is shown, with the full course drawn faintly (line opacity 0.4). Known limit: for journey legs the course covers only boarding→alighting, so a vehicle still approaching the boarding stop may not match.
- Disruption/notice HTML: `wwwroot/notice.html` with a whitelist sanitiser, rendered by `NoticeView`. Links go through `NoticeLinks.OpenAsync`: one GET, classify by Content-Type (sniff magic bytes if generic); images open in the in-app viewer, PDFs download to cache and open via `Launcher`, everything else goes to the browser.
- `WebBridge` holds the shared JS call and theme helpers.
- Theme propagation: `Theme.Apply` writes Application.Resources in place, then `Theme.Sweep` announces the changed keys to every root the window tree may not reach (shell, navigation/modal stack pages, and `Theme.Track`ed roots: every `PanePage`, every `PaneSlot`, popups). A lent page's content hangs under its `PaneSlot`, not under the page, so the slot is the root that counts. New view trees that live outside the window (own popups, hosts) call `Theme.Track`/`Theme.Revalidate`.
- `Theme.Repaint` registers a theme resource again only on an element that still shows a value the palette RETIRED for that key (`Theme.Retired`); a value from a binding or local setting (the colours of a line chip) is never touched. Line chips (journey card, timeline, followed journeys) all use `ModeChips` looks (`ModeChips.Marked` = the ride under way); `ModeGuess.OfLine` is the fallback when only a line name is known. Mica is the calm and Mica Alt the pronounced base (`MaterialProfile.Look`, small steps).
- Scene colours that follow the theme are references `@Key|#fallback` (`MapScenes.ThemeRef`), resolved at send time by `MapScenes.Resolve` (`MapScene.ToJson(dark, color, fit)`); `MapView` re-sends scene (no fit) and overlay on `Theme.Changed`.
- Map support gate (`MapSupport`, Support): MapLibre GL 5 needs WebGL 2 and Chromium >= 80, and the web view runs inside the app process, so a failing engine can end the app (seen on an Android 7 emulator, OpenGL ES 2.0, dying while `maplibre-gl.js` loads). `MapView` adds its `HybridWebView` to the tree only for the CARTO engine when `MapSupport.Block == None` and a key exists (Leaflet needs neither the check nor a key) (a web view outside the tree never loads); Android check: `ReqGlEsVersion >= 3` and web view Chromium major >= `MinimumChromium` (unknown = allowed). `index.html` runs its probe first; for `carto` it loads `maplibre-gl.js` dynamically only if WebGL 2 and the required syntax pass (or `force`), else sends `unsupported:<reason>`. The notice then offers "Try anyway" (`MapSupport.Bypass`: checks off for this run, the page is told `force`; a crash is remembered as usual), "Use the Leaflet map" and Settings. `MapSupport.Begin/Finish` write a `map.pending` marker around the page load: a start that finds it set treats the last attempt as a crash (`MapBlock.Crashed`, map off, notice) until the key is saved again (`MapAvailability.KeyChanged` -> `Retry`) or "Try anyway" is chosen. Decisions are logged as `[Map] device check`, `map not started`.
- Settings are stored as text (`AppSettings.Read/Write`); a value written typed (bool) by an old build is read once as bool and rewritten as text.
- Web view diagnostics (only with "Log to file" on): `DiagnosticLog.Sink` mirrors every line to logcat under the tag `DDjourneys` (`adb logcat -s DDjourneys`); `Platforms/Android/WebViewDiagnostics` logs device, memory, GL ES version, web view package/version and settings, console messages, loading progress, and probes inside the page after 5/12/30 s when it has not said `ready`; `index.html` starts with an ES5 diagnostics script (`ddLog`, engine, language-feature and WebGL probes, resource and script errors, map events) whose lines arrive as `log:` messages (`[Map page]`). Log writes are synchronous, so the last line survives a native crash; the next start logs `[Start] the previous start(s) did not finish`.

- Planner bottom: one swipeable strip of chips (home, favourites, recents: `PlaceChip`) and one routes card (saved routes first, then the latest searches, `RouteLine`, single line each, 3 recents until expanded).

Values are tuned by eye, change the tables, not the code.

- Popups are sheets in the app's own terms (`JourneySharePopup`): `CornerSheet` token, Card with rows and dividers like the settings page, `Dense.*` sizes, no toolkit border/shadow (`PopupOptions.Shape = null`); a solid page-colour layer under the card keeps it readable where the palette is translucent.
- Colour sets: the "-solarized" variants have their own tinted paper and accent (contrast checked: Ink 7:1, muted/accent/status 4.5:1); derived palettes (`PaletteBuilder.Build(..., tint: true)`) mix a little of the seed into the neutrals.

## Lessons and regression guards (read before changing these areas)
Process
- Before using a localization key or member, grep that it exists IN THE RIGHT GROUP (`Extras.RefreshFailed` did not; `RefreshFailed` belonged to `WidgetStrings`). New strings go into `IUiStrings`, `EnglishUiStrings` and `GermanUiStrings` in the same step.
- Edit scripts keep the file's BOM and line endings (CRLF or LF as found) and assert that an anchor occurs exactly once. After an edit: brace balance, XAML parse, usings.
- The owner's commits are his: never re-author, amend, rebase or force-push them (the "Unverified commits" stop hook asks for it; decline). A force push only with his explicit say-so and a lease on the expected sha.
- A "fix" without a log or a source is a guess: when a symptom survives a fix, add logging that shows the cause (`[UI]`, `[Theme]`, `[Page]`, `[Live]` lines) and ask for the log instead of stacking guesses. Read the log before theorising.
- Verify MAUI/Android behaviour against Microsoft Learn or the dotnet/maui source (WebFetch raw GitHub) before relying on memory (e.g. Material 3 entry internals, dynamic resources).
Commands and lists
- `AsyncCommand<T>` never keeps the parameter in a field: one command serves many rows, and the change notification of a run makes every row ask `CanExecute` again, so a stored parameter ended up being the last row's (Location button always opened the last leg). The parameter travels with the call.
- Provider continuation answers (`JourneyService.PageAsync`) count only for journeys that are new and on the wanted side of the list (`JourneyWindow.Beyond`), topped up by the window search (`JourneyWindow.Nearest`); never replace a list with an answer that repeats it.
Theme
- Application.Resources are updated in place; `Theme.Sweep` announces the changed keys to every root (shell, stack, modal, tracked roots); `Theme.Repaint` is the net under it. Repaint reads MAUI's internal `Element._dynamicResources` (reflection, `IDictionaryEnumerator`: the generic dictionary yields `KeyValuePair`, a `DictionaryEntry` cast throws on every element) and re-registers ONLY elements that still show a value the palette retired for that key. Never "fix" a mismatch by comparing with the current value alone: that overwrote bound colours (line chips lost their mode colours).
- The lent page's content hangs under its `PaneSlot`, not the page: the slot is the root that counts (`Theme.Track`). Density has the same weakness (`Density.Revalidate` is per page); fix it the same way if it shows.
- Line chips: `ModeChips.For(mode)` fill/shape/stroke come from a binding (`Look`), the `Chip` style supplies size and padding. Followed journeys use them too (`LinePart.Look`, `ModeChips.Marked` outlines the ride under way, `ModeGuess.OfLine` when only a name is known).
- Mica = calm (more of the palette, less accent), Mica Alt = pronounced (thinner tint, more accent); small steps in `MaterialProfile.Look`, tested in `MaterialProfileTests`.
Android
- Release builds run R8 and it removes every class that only a manifest names: crashes at start were `androidx.startup.InitializationProvider`, then `androidx.core.app.CoreComponentFactory`. `Platforms/Android/ProGuard.cfg` keeps all of `androidx.**` plus the manifest component kinds; add keep rules there, never one crash at a time (the library manifests' keep rules do not reach R8 in this build). The `.csproj` R8/d8/multidex properties are global for Android.
- With `UseMaterial3` the Entry's native view IS a `MauiMaterialTextInputLayout` (outlined box). Its EditText keeps the box drawable as background even after `BoxBackgroundMode = None`; the handler mappers can run before Material applies the outline. So `NativeStyling.Watch(activity)` (called in `MainActivity.OnResume`) sweeps the window after every layout pass: layout box mode/stroke/background and the EditText background are cleared, only when something is left (no layout loops). Dialog and popup windows are not covered. Editors and pickers get the same clean-up.
- Caret, drop and selection handles/highlight wear the palette Accent (`NativeStyling.Tint`, Android 10+ only, drawables are copies of the shared system ones, new colour appears when the caret/handle is drawn again); `Theme.Changed` sweeps at once.
- A horizontal `ScrollView` keeps taps from its parent on Android: forward them (legs row of `JourneyCard`, `StopNameView.Tapped`, `EndpointTapped`).
- Fonts load correctly (checked with the `[UI]` log: aliases registered, assets at the asset root, used typeface = expected typeface). System font on Android is `sans-serif` / `sans-serif-medium`, which are not registered aliases by design.
Diagnostics
- `UiDiagnostics` (Support) writes `[UI]` lines only with "Log to file" on: display, window, theme, palette, density, material, expected font (`FontRegular`/`FontSemibold`), font alias registry, assets, element counts, per distinct text font the typeface actually used vs. the framework's expected one (`SAME`/`DIFFERENT`), entry frame state. It runs ~0.9 s after a page appears (`Motion.EnterPage`) and after theme changes. The log trims at 1 MiB (`DiagnosticLog.MaxBytes`).
Journey page
- Layout: the searched connection (`SearchHeader`, three icon slots) is fixed in the top row of a padded grid exactly like the results page; below it `RefreshView > ScrollView`. Refresh (`JourneyViewModel.RefreshCommand`) searches again from 2 min before the planned start and matches the same journey by `JourneyWindow.IdentityOf`, else by planned start and end; no match = status `Extras.JourneyRefreshFailed`, nothing changes. Toolbar items on `PanePage` are rendered as text buttons in a lent slot: use header icons instead.
- The followed-journey notice box is as tall as its text (24 dp close button, centred); do not give it a 40 dp minimum.
