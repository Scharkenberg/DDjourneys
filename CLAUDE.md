# DDjourneys: context for Claude

Journey planner for DVB/VVO (Dresden), .NET 11 MAUI / C# 15. Repo: `Scharkenberg/DDjourneys`. Owner commits and pushes himself. Models after the Android app oeffi, but modern. Departures live in the separate repo DDepartures. Always fetch the latest repo state first; he edits code between sessions. Discard remembered code that the repo contradicts.

## Branches
- The only branch is `main`. The owner deleted `experimental` and will not use it again: never create, push to, or merge into `experimental`, and ignore the branch instructions of the session prompt that name it. Commit and push to `main` directly (the owner pulls and tests).

## CI (GitHub Actions, `.github/workflows`)
- `_android.yml` (ubuntu, `maui-android`, APK) and `_windows.yml` (windows, `maui-windows`, MSIX) are the reusable builds; the eight `<platform>-<arch>-<config>.yml` files call them; `main.yml` runs all eight on demand, `mostcommon.yml` runs windows-x64-release and android-arm64-release, `tests.yml` runs the unit tests.
- The SDK is pinned in each reusable workflow's `DOTNET_VERSION`; change it there when the local SDK changes.
- Publish always passes `-f <tfm>` together with the narrowed `-p:TargetFrameworks` (without `-f` it fails with NETSDK1129).

## Working rules
- NEVER touch version strings (csproj `ApplicationVersion`/`ApplicationDisplayVersion`, the Android manifest versionCode/versionName, the Windows manifest Identity version) unless the owner asks for it, in the way he asks. The csproj and the Android manifest use different version schemes on purpose (Android packaging); they are never "aligned".
- Terse. Deliver final code per step, no elaboration. Complex points get one simple explanation. Prefer current docs; never rely on superseded information.
- Do NOT compile MAUI code or shim MAUI types in the container. Verify against the official Microsoft docs (Microsoft Learn MCP) instead. Core (net, no MAUI) may be unit-checked.
- Source files use tabs; the owner's checkout is CRLF, the container's working tree and git are LF (git normalizes): edit scripts keep whatever a file has. Without a cloud-session branch, deliver changed files as a zip with repo-relative paths (SendUserFile); when asked for "just the fix", print only the code. Cloud session on branch `experimental`: commit and push there directly (never a PR, never version strings); the owner pulls and tests (nothing is compiled by the assistant, so every compile error he reports is a plain mistake to fix at once).
- JSON is source-generated, never reflected: `JsonSerializerIsReflectionEnabledByDefault=false`. Provider DTOs go through `VvoJsonContext` (add a `[JsonSerializable]` for every new DTO root); wire objects without a DTO are `JsonObject` trees (`Wire.Array`, no anonymous types, they are trimmed away on Android); stored lists are written with `StoredJson.Write(items, toNode)`. `ExpertReport` reads DTOs through `VvoJson.TypeInfo`. No `yield` inside catch; regexes are `[GeneratedRegex]` (SYSLIB1045; the class and its outer types are `partial`).
- Analyzer baseline (C# 15): collection expressions everywhere (`[]`, `[.. x]`), field-backed `get;`, primary constructors, `Lock`, null-conditional assignment, UTF-8 literals, `CancellationToken` always last (CA1068; positional ct-only calls become `cancellationToken:`), `FirstOrDefault()` on lists as `Count > 0 ? x[0] : null` (CA1826), types that implement WinRT interfaces are `partial` (CsWinRT1028). In the app project a collection expression that targets `IReadOnlyList`/`IEnumerable` is cast to a concrete type (`(List<T>)[.. x]`, CsWinRT1032). XAML-bound constants are `const` with `{x:Static}`, localized text uses `{localization:Tr}` (no instance property just to read a static).
- Dependencies: CommunityToolkit.Maui, plus MAUI's own `Microsoft.Maui.Controls.Foldable` (`$(MauiVersion)`, `UseFoldable()`). Own ObservableObject/AsyncCommand, built-in DI and Shell.
- Verify before finishing: brace balance, XAML well-formedness, every `{localization:Tr Group.Key}` exists, usings, no leftovers.

## Shell: phone tab bar
- `AppShell.xaml` defines BOTH doors: a `TabBar` (`PhoneTabs`) with four tabs — Plan (`Route="plan"`), Departures (`"departures"`), Map (`"map"`) and More (`"more"`, the SettingsPage hub) — and the `ShellItem` `SingleDoor` (the planner, content route `plan`, every other form factor). The `AppShell` constructor keeps the one the form factor needs and removes the other (`DeviceInfo.Current.Idiom == DeviceIdiom.Phone` → tabs; tablet/desktop → single door) before anything is shown. Removal is load-bearing: with both doors in the tree `//plan` would be ambiguous, and because Shell builds a tab page only when its tab is first opened, no second PlanPage exists anywhere.
- Tab CONTENTS carry no explicit routes (only the Tabs do): a relative push of `departures`/`map`/`settings` then always resolves to the globally registered route (a push on top of the ACTIVE tab) and can never hit Shell's "Relative routing to shell elements is not supported" trap, which fires when a relative route matches a hierarchy node of the current section (it would fire if the current tab's ShellContent itself were named `departures` and something pushed `departures`).
- Landing on one of the four root pages goes through `Support/TabRoots.OpenAsync(route)`: on the phone it switches the tab with an absolute `//<tab>` route (Settings maps to `//more`), which also unwinds that tab back to its root; everywhere else the page is pushed as these calls always did (only `Routes.Plan` means "back to the start": `Panes.ToStartAsync`). Callers: the planner's toolbar buttons (settings, map, departures), Settings' "explore the map", the map notice's settings button, `AppShortcuts` "departures from here" (`//departures`, then the tab's default board locates), `ContractInbox.ShowAsync` for the parameterless map. Every PARAMETERIZED variant of a tab-root page type (a stop's board, a map with a scene or a centre, arrivals at a stop) stays a relative push on top of the active tab — never re-rooted into the tab.
- Start screen (Settings > Start, phone only, `AppSettings.StartScreen`: Planner default / Map): the AppShell constructor sets `PhoneTabs.CurrentItem` to the map tab before anything is shown — no navigation, no flash; the setting is honored on the phone only and the chooser is hidden elsewhere (`StartSettingsViewModel.HasTabs`).
- `Panes.ToStartAsync` (`//plan`) still lands on the planner root (the absolute route pops the plan tab's stack) and now closes panes on EVERY tab's stack (`Panes.StacksOf`), not just the current one — a foldable can keep panes open on a background tab.
- Shell facts this relies on (verified against the MAUI source, `ShellUriHandler`/`ShellNavigationManager`/`ShellSection`): absolute `//x` routes must name a hierarchy node (absolute routing to a global-only route throws) and a pure hierarchy navigation pops the target section to its root; other sections keep their stacks; `IShellContentController.Page` returns the cached page without creating it.
- Android back (button and gesture, `Platforms/Android/TabBackCallback`, registered before the pane callback): never ends the app except on the plan tab's root. The callback is enabled ONLY while another tab's bare root is in front (`Stack.Count <= 1`, no modal, no pane; re-evaluated on `Panes.BackChanged`, which every shell navigation raises), so predictive back knows in advance and MAUI pops pushed pages, panes and modals as always.
- rc2 back facts (MAUI source): `MauiAppCompatActivity` adds its own AndroidX `OnBackPressedCallback` in `base.OnCreate`; callbacks added later are asked first (newest first). `ShellSection.Stack` starts as `{ null }` for the root, so a bare root counts 1. At a root `Shell.OnBackButtonPressed` raises a Navigating `Pop` that pops nothing (AppShell skips the exit animation for it). Static subscriptions of activity callbacks end through `LifecycleEnd` (the activity can be recreated).
- Shell query rule: `ApplyQueryAttributes` is NOT called on a tab-root page reached with an empty query - a tab root must set up its default state in `OnAppearing` (MapPage: `_query is null`).
- Tab icons and colours: the icons are the app's own geometry as SVG images (`Resources/Images/tab_*.svg`, drawn from `IconGlyph.cs`, black strokes so the bar tints them; `Tab.Icon` in AppShell.xaml). The bar's colours ride on the shell appearance - the `Shell` style (Controls.xaml) sets background, active icon, active label and the unselected tint, and Material's pill behind the active icon is coloured natively (`Platforms/Android/TabBars.cs`, `AccentSoft`, following `Theme.Changed`). Limits accepted: the labels keep Material's font and size, and the icons do not scale with the app text size.
- Documented risks, accepted: (b) every tab keeps its own navigation stack, so cross-tab jumps must use the absolute `//` routes — never a relative push of another tab's root; (c) parameterized instances of tab-root page types are pushed, never re-rooted — the same stop can be open as the departures tab's default board and as a pushed board above another tab at the same time; (d) tab pages stay alive once visited (state preserved across tab switches; Shell's `EvaluateDisconnect` only drops a section's page when the whole ShellItem stops being current, which never happens with one TabBar) — MapPage's `OnDisappearing`/`OnOwnVisibility`/`UpdateVehicleStream` pattern pauses the vehicles stream while its tab is not shown, and real teardown still happens on pop/replace (`LeaveIfGone`).

## Wide windows (panes)
- Plan, Results, Journey, Map, Departures, Run and Vehicles derive from `Support/PanePage` (XAML root `support:PanePage`). Panes: one per `PaneRules.MinPaneWidth` (360 dp; 720 = two, 1080 = three ...; `Hysteresis` 40; at most `MaxPanes` 5). With room for two or more, the current Shell page is the host: a page opened from it that pairs (`PaneRules`: Plan>Results, Results>Journey, Journey>Map/Vehicles, Departures>Run, Run>Map/Vehicles) is lent to it, not pushed. The host shows the deepest pages of its chain that fit; each step shifts the chain one column left; a resize shows more or fewer of the same chain. Narrow windows keep the plain Shell stack.
- Back always closes the deepest pane first, in every path: Android back and predictive back gesture (`Platforms/Android/PaneBackCallback`, an AndroidX `OnBackPressedCallback` enabled while `Panes.CanGoBack`, following `Panes.BackChanged`), the Shell title-bar back (`BackButtonBehavior`), `Page.OnBackButtonPressed`, and the panes' own back arrow (left-most visible pane, whenever the host's title bar offers no back: start page, or host content hidden) and close button (deepest pane). `Panes.GoBack()` is the one entry point.
- Pane motion (`PanePage.Animate`): one `Animation` drives all panes (FLIP: old on-screen x minus the exact new cell x from `PaneFrame.LeftOf`, set in the same pass as the cell); a new arrangement takes over from a running one; `Motion.QuietEntrances` mutes card entrances meanwhile. `PaneFrame` replaces grid definitions only when the shape changes and sets a cell only when it differs.
- Default font: System (`FontCatalog.SystemId`); a stored choice is kept.
- Lent pages are full pages created through DI and never pushed: `Panes` applies the query to page and view model like Shell, moves the page's content into a `PaneSlot` (header with title, toolbar items, close) and drives `OnAppearing/OnDisappearing` itself. Width changes replace the pages by new instances on the same view models (`PaneRules.Recreate`, `Panes.GatherAsync/SpreadAsync`; state outside the view model goes through `RecreationQuery`, e.g. the map scene; `OnRetired` releases the old page's subscriptions). A view with native views is never moved to another page: the page's own content sits in the frame from construction (`PanePage.SetFrame`). Back to the start: `Panes.ToStartAsync(shell)` (closes all panes) instead of `GoToAsync("//plan")`.
- Rules for these pages: navigate with `Panes.GoToAsync(route, parameters, from)` (`from` = the page or view model asking; without it the call is a Shell push) and `MapScenes.OpenAsync(scene, title, from)`; call `LeaveIfGone(args)` in `OnNavigatedFrom` instead of `PageTeardown`; dialogs through the page's own `DisplayAlertAsync/DisplayActionSheetAsync` (redirected to the host while lent), popups on `DialogPage`. A new pair is one line in `PaneRules` plus the `from` argument at the call site. Log lines `[Panes]`.
- Foldables: the frame (`Support/PaneFrame`) is MAUI's `TwoPaneView` (`UseFoldable()`), configured to split only across a fold; its own row/column sizes after measure give the fold position inside the frame (`FoldLayout`). Its two pane containers stay empty (a view moved between them would change parent); all panes live in one grid (`PaneFrame.Strip`) spanning the frame and only change cell. Vertical fold: panes split between both sides (each side as many as fit, at least one, deepest on the far side, nothing on the hinge); on a tri-fold MAUI reports one fold, and the two-section side gets two equal columns, whose border is the other fold. Horizontal fold (tabletop), only where the width already splits: the deepest pane above, the others in columns below. MAUI counts a flat foldable as spanned (ignores `isSeparating`).
- Never move a view that already has native views into another parent (Windows breaks: stale measures, empty content, flicker). Build structure before the handler exists (`PanePage.SetFrame`, `PointerLight` installs its overlay on `HandlerChanging`, `StopNameView.SingleLine` set from XAML); panes only change their cell in `PaneFrame.Strip`.

## TRIAS (VDV 431-2, schema v1.4, checked against github.com/VDVde/TRIAS)
- A `Service` keeps its line data in `ServiceSection` (LineRef, DirectionRef, Mode/PtMode, PublishedLineName, OperatorRef); `TriasMapper.Properties` reads the first section, or the service itself for older flat responses. Destination, JourneyRef, Attribute and the status flags stay on the service.
- Journey stops are identified by stop place (`StationId`: first three DHID parts), the platform is a detail. Changes are `InterchangeLeg` (`InterchangeMode`: walk, protectedConnection, guaranteedConnection, remainInVehicle; `WalkDuration`, `BufferTime`) or `ContinuousLeg`; only the connection modes are guaranteed.
- Versions: every request is written for 1.4 and steps down 1.3, 1.2, 1.1 (`TriasClient.SendAsync(kind, build(dialect))`, `TriasDialect`). Rejected = non-transient HTTP error, unreadable XML, or an `ErrorMessage` without any result and not a "no result" code. The working version is remembered per `TriasRequestKind` and 1.4 is retried after 30 min. Unreachable/timeouts never downgrade. Each attempt is logged (`[TRIAS] ...`). The VVO's server (`efa.vvo-online.de/std3/trias`) answers HTTP 400 to 1.4 and 1.3 and accepts only 1.2 (seen in the log: the step-down is not optional there), and it quotes no `TripFares` (see "FareBorrower"). Only 1.4 is in VDVde/TRIAS; which optional parameters older versions know (`HasExtendedContent` from 1.3, `HasMobilityAdditions` 1.4) is an assumption.
- Request parameters are an XSD sequence: keep `TriasRequests` in the order of `TripParam`/`StopEventParam`/`TripInfoParam` (1.4: `InterchangeLimit`, not `TransferLimit`; it is a positive integer, so "no transfers" is filtered client-side).
- TripInfo (`TriasRequests.TripInfo`, `TriasMapper.MapRun` → `RunDetail`) refreshes a run from `JourneyRef` + `OperatingDayRef` kept in `TriasRunData`; falls back to the stop event's calls. `IDepartureProvider.GetRunDetailAsync` (default: stops only) carries `RunDetail.Vehicle` (`CurrentPosition`) and `OperatingDays`; the Run page shows operating days and `MapScenes.FromRun` adds a reported-position vehicle marker (and then prefers the static map over the live lookup).
- `FaresParam` (`PassengerCategory`, last element of `TripParam`) is sent from 1.4 on for non-adult passengers (`RoutingPreferences.Passenger`, option "Tickets for" on the routing page, per provider). `IncludeOperatingDays` from 1.3; `OperatingDays` (From/To/Pattern bit string, description) → `JourneyLeg.OperatingDays`, shown on the leg as "Runs Mon–Fri" (`OperatingDaysText`, nothing when daily).
- Situations: `Situations/PtSituation` (SIRI SX: SituationNumber, Summary/Description/Detail) are matched to `SituationFullRef` on the trip and its legs and become `Journey.Notices` / `JourneyLeg.Notices`. Call-level `Occupancy` fills `RunStop.Occupancy`.
- Not implemented: `CurrentPosition` on journey maps (only the run map), traveller age/owned tickets in `FaresParam`, Trias_Booking/Facilities/Alerts.

## Journey page actions, followed journeys, input mode
- Icons for maps: `MapPin` = live tracking of one vehicle or trip (leg button on the journey page, run page, followed journeys); `Map` = a map that does not follow one vehicle (journey overview, stop surroundings, pick on map). The leg action row (`LegRow.HasActions`) is pin + "Earlier" + "Later" (short words, long hints as accessibility descriptions).
- Earlier/Later on a ride (`JourneyService.GetLegAlternativeAsync`): the provider's own continuation (VVO `tr/prevnextmove`) is asked first and its answer counts only if the ride really moved to the wanted side (`LegAlternatives.Pick`: same line and stop, planned departure moved by more than 30 s); a provider that answers with the same ride, nothing, or fails falls through to `LegAlternatives.ComposeAsync`, which works for every provider: direct connections between the two stops of the ride (`MaxTransfers.None`, no alternative stops) are searched, the nearest earlier/later one (same line first) replaces the ride, and when it no longer connects with the leg after (later) or before (earlier) that part is planned again (`JourneySplice`: legs + transfers re-indexed, flags of the old pair reset). A composed journey has no session (`Id`/`Context` null: no PDF, no provider continuation), so the buttons (`JourneyViewModel.HasLegAlternatives`) depend only on the journey having a ride. Log lines `[Leg alternative]`. The view model never loads the same journey again (no-op answers were the "RAM grows per click" symptom) and shows `Journey.LegSearching` while it works.
- Via (`ViaRouting`, applied by `JourneyService.SearchAsync` to every provider): the provider is asked with the stop-over, only journeys that really pass it (`ViaRouting.Passes`: stop of a ride, transfer, same name or within 120 m) are kept; none (provider ignores it, refuses it for address/POI endpoints, fails) -> two ordinary searches (start -> via, via -> destination, fitted by time, 1 min stay) are joined. Earlier/later pages of a via search are windows of that search (no native continuation). Log lines `[Via]`.
- Bike feeder (B9, "bike to the stop", `BikeFeeder` + `BrouterClient` in Core): opt-in per provider in Settings > Routing preferences ("Cycling" section: switch + radius 1-5 km, default 2, `bikeFeeder`/`bikeFeederRadius` in `AppSettings`, reset with the routing defaults). It applies only when the start is NOT a stop and has coordinates (`BikeFeeder.Applies`) and the query has no stop-over (the two special modes are never stacked). Flow: stops within the radius (`StopAreaService`, at most the 6 nearest), each with a BRouter track (`brouter.de/brouter`, profile trekking, GeoJSON; `TtlCache` 10 min per point pair, failures never cached); the boarding stop is the flattest among comparable rides (at most 5 min slower than the fastest; ties: faster, shorter, id); the transit part is an ordinary provider search from the boarding stop (departure mode: asked for `now + ride + 2 min parking buffer`), and the bike becomes a REAL first leg (`TransitMode.Bike`, `JourneySplice.Assemble` with the transit journey as its part, so following follows the vehicles). The feeder leg carries `DistanceMeters`/`AscentMeters`/`DescentMeters` (ascent = BRouter's "filtered ascend", descent derived from it minus the ends' height difference, never below 0) and renders as a chip/timeline row/map line with the compact summary ("1.1 km · +5 m ↑ · −3 m ↓ · 8 min", `Journey.BikeSummary`, the chip and row formats share it). A departure-mode journey whose bike would start before the asked time is dropped, not shown impossible; arrival mode fits the bike in front of whatever was found. When NO track can be planned (offline, no stop), the ordinary search answers and its journeys carry the marker notice `dd: bike-feeder-unavailable`, worded in the user's language where notices are shown (`JourneyViewModel.WordNotice`; the technical view shows the marker). When the boarding stop has no transit, the feeder stays quiet (nothing was wrong with the bike). Pages of a feeder search are windows of that search (no native continuation; a shown feeder journey also disables it). `TransitMode.Bike` is NOT a ride (`TransitModeExtensions.IsRide` excludes it: transfer counts, feasibility and the card endpoints stay honest), never enters stored formats (widgets and the board cache parse modes tolerantly by name and never see feeder legs). Log lines `[Bike]`. `BrouterClient.Parse` treats an EMPTY `features` array as unreadable (the `JsonNode` indexer does NOT bounds-check - `[0]` on an empty array throws).
- Timeline rhythm (`JourneyPage.xaml`): text column padding top 4, bottom 12 (intermediates 8), spacing 4 (leg column 6); the notice card margin 4,12.
- Settings must do what they say: a control that the selected provider ignores is hidden (`ProviderCapabilities`: `WalkToStops`, `SupplementFilter`, `RouteOptimisation`, `PassengerFares`; `RoutingSettingsViewModel.Show*`), a setting that only applies somewhere says where in its text (occupancy and platforms: "in journey details"). `AppSettings.TimeoutSeconds` sets `ApiClient.DefaultTimeout`, so it holds for every call that names no timeout.
- About page: the README (repo root) is an `EmbeddedResource` (`DDjourneys.README.md`), and `LIESMICH.md` its German twin (`DDjourneys.LIESMICH.md`); `AboutPage.ResourceFor(language)` picks German for "de*", else English. Read by `AboutPage` and shown by `MarkdownView` (native controls) via `Core/Documents/MarkdownDocument`. The READMEs are for laypeople: prose with headings, no lists, no bold, no quotes (tests enforce it). Both files must always be kept in sync: every change to one is made to the other in the same step (`ReadmeLanguagesTests`: same sequence of headings and paragraphs, same links and code spans).
- Performance rules: `ApiClient.CreateHandler()` (SocketsHttpHandler, gzip/deflate/brotli, pooled connections) is the one handler; every `RelativeSource` binding carries `x:DataType`; looping animations (`Motion.Breathe`, `Skeleton`) wait for `Motion.WaitUntilWorthAnimatingAsync` and run only on the page the user sees (`Motion.IsShowing`); Android shortcuts are published only when labels or build changed.
- Journey page actions are icons in the overview card (`JourneyActions` in `JourneyCardModel.Actions`, left of the map icon): PDF, hand-over to another app, follow (bell, solid when followed; a tap toggles), pause/resume (only while followed), and the notice badge (warning icon + count, scrolls to the notices; on result cards it is a plain badge). A followed journey shows one slim tappable strip (opens the followed journeys). `IconButton.TargetSize` (44 default) lets rows of several icons use 38-40.
- Walks at both ends of a followed journey: the service follows vehicles only, so `FollowedWalks` (Support, written in `SchutzengelJourneyTracker.FollowAsync`, dropped with the journey) keeps the leading and trailing walk (transfers before the first / after the last ride, plus walking legs there) and `TripTimeline.SetWalks` adds them as footpath episodes with real-time-shifted times. The journey therefore starts when the walking starts and ends at the destination; the live content says "Walk to X" + "From t1 until t2" (`NotifWalkFromUntil`), `TripSnapshot.IsFinalWalk` marks the last walk.
- Followed journeys never vanish from one bad answer (`SchutzengelJourneyTracker.SyncPlanListAsync`): a plan missing from `plansMinimal` is asked for directly (`IsGoneAsync`, `planRawData`; only "no such plan" counts), then needs 3 lists in a row and 10 min since it was last listed; a plan is hidden as "replaced" only by ANOTHER plan naming its trip; a missing token never clears the cache; a 401 is repeated once with the same token before the account is replaced (a new account loses every plan).
- Followed journeys page (`TrackedJourneysViewModel`): fetch interval 20 s while a journey is under way, 45 s when one starts within 90 min, 3 min otherwise, 15 s after an error; between fetches the rows follow the clock every 10 s (`Reconcile`: planned becomes under way, past arrival becomes arrived, progress moves on from the last answer); the next answer replaces it all.
- Input mode (Settings > Start, `StartSettingsPage`): `AppSettings.StartInput`, `StartFrom` (device position or a chosen place), `StartFromPlace` (per provider; picked through the place search with `Routes.TargetStart`, any stop, address or POI, not added to the recents). Once per start the planner fills the start and opens the destination search (`PlanViewModel.StartInputModeAsync`); a pending contract request or quick action wins (`ContractEntry.HasPending`, `AppShortcuts.IsBusy`).
- The departures page pins the stop line and the departures/arrivals/now row; the planner's From/To/Via cards use 38 dp icon targets and 50 dp rows.

## Departures page
- Line filter: a chip row above the board filters the FETCHED board client-side, never a new request. The pure logic is `BoardFilter` (Core): a departure shows when its line is among the picked keys (`BoardFilter.LineKey` normalises spaces and case, the rule `LineCourseService.SameLine` uses for boards) and it is not cancelled; the "show cancelled" chip lets cancelled rows back in struck through (`DepartureRow.TextDecorations`) — hidden is the default. Chips: tap toggles (multi-select), long press keeps only that line (CommunityToolkit `TouchBehavior` in the `mct:` namespace; a long press on the only picked line clears the filter), the "All lines" chip clears. All of them are `Border`s with `ChipButton` + `support:Themed` (the routing-preferences pattern). The chip set is the stop's own lines (loaded with every stop now; `TtlCache`d ten minutes) plus whatever the current board shows; the collection is left alone when nothing changed (a rebuild would jump the scrolling row), and a pick resets with the stop and the provider.
- Nearby previews: the nearby rows show their next departures inline (one departure collapsed, up to three when the strip is tapped; line chip + "3′"). The data path is `NearbyBoards` (Core) — the ONE fetch shared with the "next departures around" widget: `WidgetLoader` calls `NextOfAsync`/`LoadAsync` with identical queries (a line filter asks for three times the rows kept, the same gate of three stops at a time, a failed stop answers empty); the log prefix of a failed stop is now `[Boards]`. The page loads its previews staggered, one row at a time, nearest first (the nearby list is sorted by distance now, as the widget's is), at most eight rows per pass (three shown plus `Spare` asked), cancelled with the page; a new locate or a refresh the passenger asked for restarts the pass, the 30-second board pass does not touch it. `NearbyBoards.Previews` picks what a row shows (not cancelled, not gone) — pure, unit-tested.
- Line search: a query that names a line ("11", "85", "S 1", "RE01" — `LineIndex.IsLineQuery`: up to three letters, one to four digits, an optional trailing letter, spaces ignored) makes the place search offer "Line {0} — show course" rows above the place results. The candidates come from the `LineIndex` (Core singleton, in memory only — no stored schema, nothing persisted; it refills as stops are opened): `DepartureService` (every board) and `NetworkService` (stop lines) feed it per provider as a side effect of normal loads; entries dedupe by normalised name (the stop last seen is kept, an unknown mode may become known), age out after 30 days and are capped at 400 per provider. Tapping opens `LineCourseService.BothDirectionsAsync` from the stop where the line was last seen — the same map the departures line rows open (`PlaceSearchPage.LineTapped`).
- Cached last boards (B7): every successful now-board fetch — the departures page and the widget board passes alike (`WidgetLoader.BoardAsync`, with the widget's own provider id) — writes `BoardCache` (Support, the file `boards.cache.json` in the app data - a Windows setting value may not exceed a few KB, the 30 boards did; an old preferences value is migrated away on first read). The list is `BoardCacheList` (Core, pure, unit-tested): one entry per provider, stop and board mode (`Location.Id`, not the departure's `StopId`), LRU with the newest first and at most 30 boards, the departures stored in the shape the board view shows (line, mode, direction, scheduled and live time, state, platform and kind, occupancy, route changes; `ProviderData` is never stored, a run is asked for again when opened). A failed fetch shows the cached board with `Departures.CachedBoard` ("...the board as of {0}", `Format.Time` of the stored fetch moment) — only when nothing is on screen (a silent pass keeps its rows, which are at least as fresh) and only for a now-board; a cache miss is today's error path, unchanged. A failed widget pass keeps the widget's own snapshot as before (`IsStale`, never rebuilt from the board cache — that would only help a widget that never succeeded once). App-side schema `board-cache` r1.

## Fares
- `JourneyFare` (kind, price, zones, notes, valid-for, url). VVO: `VvoFareMapper` turns the route's `Price`/`PriceDayTicket` (+ zone names, `TicketNotes`) into a single and a day ticket; a named `Tickets` list beyond those two is shown as the provider words it (see the ticket advice section). TRIAS 1.4: `TripFares/Ticket`. `FareChoice.Preferred(fares, passenger)` picks the one ticket cards, header and shares name: the passenger's own single ticket, else tickets without a passenger statement (VVO quotes only the normal price), else adult. The journey page section is collapsed by default (header: preferred ticket and price; expanded: compact rows, zones and conditions once).
- A change is "endangered" only by arithmetic once real-time times exist on either side (`TimelineBuilder.CreateBoundary`); the provider's flag counts only without real-time data.

## Ticket advice
- The ticket advice of a journey is ONE card above the fares card of the journey page; its words are composed in ONE place (`JourneyViewModel.BuildTicketAdvice`, the `JourneyFacts` discipline). The numbers come from `TicketAdvisor` (Core, pure, unit-tested): zone count, single-versus-day break-even, Deutschlandticket amortization, coverage verdict and the BahnCard 25 estimate.
- Zones come from the fares the provider quotes (the only zone engine there is): the zone names of `JourneyFare.Zones` ("Dresden, Radebeul" are two), else the count as words in `Description` ("1 Tarifzone"; a regex over `NumberOfFareZones`-style text, so a TRIAS "Preisstufe" or "P1D" never counts as zones). The zone plan feature marks a journey's end stops only; it computes no zones.
- Coverage verdicts, from the data only: fares with zones → `WithinVerbund` (a Deutschlandticket covers the regional journey); any `LongDistanceTrain` leg → `LongDistance` (warning: the ticket does not cover long-distance trains); no zone data → `Unknown`, and nothing is claimed (a cross-border journey cannot be told from the data, so it is not warned about either).
- `AppSettings.HasDeutschlandTicket` (global pref, not provider-scoped): the toggle lives in the Tickets section of the routing settings, which is shown for providers with the `Fares` capability (`ShowTickets`); the passenger list inside stays behind `PassengerFares`. When the toggle is on and the verdict is `WithinVerbund`, the quoted fares are struck through (`FareRow.IsStruck`/`TextDecorations`), their buy buttons are gone (`Link` null) and the fares header says "covered by the Deutschlandticket" instead of naming a price. Results cards and widgets keep their current fare wording untouched.
- The Deutschlandticket monthly price is `TicketAdvisor.DeutschlandTicketPrice` (58 €, the public VBOG price; the owner adjusts the constant when it changes) - the only place that knows it. The BahnCard 25 row is the app's own COMPUTED estimate (single × 0.75, rounded to cents), shown only for adult/senior passengers and never for a journey over a long-distance train; its `~` price, its "estimate" detail and `FareNotAll` say so - a computed value is never presented as a quoted fare.
- FareBorrower v2 scope: nothing else is borrowed. The `tr/trips` answer carries beyond `Price`/`PriceDayTicket` only `PriceLevel` (an int that duplicates the zone count - not read) and a named `Tickets` list (Name, Price, NumberOfFareZones, FareZoneNames); the list is mapped generically, deduped against the two prices by kind+price, so anything the VVO ever carries beyond single/day flows through, and nothing is invented. No week/month/BahnCard prices exist in the data (verified against the kiliankoe/vvo docs).
- alita/ALB on-demand legs: the VVO marks them by mot type `Alita`/`HailedSharedTaxi` (`VvoModeMapper` → `TransitMode.OnDemand`, the dvb-fahrplan precedent); a taxi said by the line name alone stays `Taxi`. On-demand legs are individual transport (`IsRide` false, like Taxi), so an alita-only journey has no rides. The leg carries `BookingContact` (VVO `BookingLink`, "booking hotline or URL"). The booking card (`OnDemandRow`, per leg in the timeline) shows what the data carries and NOTHING else: `OnDemandBooking.LinkOf` accepts an absolute http(s) page (the FareLinks rule) or a phone number as `tel:`; anything else falls back to the DVB Anruflinientaxi page (the authority that runs the alita lines; found through public search - vvo-online.de has no page of its own - and the reason the link is not a vvo-online.de one). Lead times, operators and phone numbers are never invented; link-out is the ceiling.
- Schema: `vvo-webapi` r2 (the Tickets list is read, on-demand mot types are recognised, BookingLink is carried). `FareLinks.VvoTicketUrl` is untouched.

## Disruptions: watched lines
- Watched lines (B4): a line the passenger wants disruption news about. Stored per provider (`WatchedLineList`, `watchedlines.list`, the `FollowedEndpointList` precedent; "S 1" and "s1" are the same line - `LineCourseService.SameLine`), written by the stars: one beside every line row of the departures "Lines" section (NOT on the board filter chips) and one in the run page header. `WatchedLines.Toggle` is the one writer; the run page freezes the provider with its departure (`RunViewModel._providerId`), the departures page uses the stop's provider.
- The check (`WatchedLines.CheckAsync`): fetch the route changes, report each watched line's active disruptions (`LineDisruptions.Report`), fingerprint them (FNV-1a over sorted id|published stamps - re-published text is a change, provider order is not) and compare with the last stored state (`watchedlines.state`, `WatchedLineStateList`; only the checked provider's states are replaced). The first sight of a line is a baseline (`FirstSeen`), never news - the passenger saw the current state when they watched the line. One check at a time (`CheckGate`); nothing is fetched for an empty watch set. Failures propagate (callers keep what they show).
- The session view (`WatchedLineStatus`): fed by every check AND by every answer the app already has (`Adopt` - the disruptions page, so opening it is enough); `RefreshAsync` stays quiet for ten minutes after any answer. It feeds the planner banner ("N of your lines are affected", `PlanViewModel`, dismissible - dismissal remembers the disruption ids for the session, so the banner returns only when a NEW disruption appears) and the disruptions row of the More tab (`SettingsPage`, `ShowDisruptions` gate, count or "no current disruptions" in the row text).
- The disruptions page pins a "Your lines" section above its list (the same `DisruptionCard` template, shared as a page resource between the CollectionView and the section): the active changes that name a watched line, independent of the page's filter and short-term switch; when nothing is watched the section teaches how to watch (`WatchHint`).
- Auto-watch seam (W1-B4b wires the platform half - WorkManager, notification channel, tracking notification): while a journey is under way its ride lines join the watch set ephemerally - `LineDisruptions.RideLines(journey)` collects them, `LineDisruptions.WatchSet` unions them with the stored lines (normalized, never stored), and `WatchedLines.CheckTrackedAsync(network, providerId, rideLines, ct)` answers exactly the CHANGED lines among those ride lines (the stored lines are checked in the same pass). The periodic background work is scheduled only while the list is non-empty; the platform layer re-reads `WatchedLines.Load()` after every toggle (B4b adds its sync hook there - nothing Android-specific lives in Support).
- The platform half, Android (W1-B4b, `Platforms/Android/Disruptions`): WorkManager, package `Xamarin.AndroidX.Work.Runtime` 2.11.2.1 (android-only reference; the package brings its own merged manifest entries - the app gains `WAKE_LOCK` and `RECEIVE_BOOT_COMPLETED` from the AAR - and its own proguard rules, nothing manual in `AndroidManifest.xml` or `ProGuard.cfg`). Unique periodic work `dd.watchedlines.check` (`WatchedLinesScheduling.UniqueName`), interval 15 minutes (WorkManager's minimum) with a network-connected constraint, `ExistingPeriodicWorkPolicy.Keep` (the interval never changes, and every app start must not push the next run out); scheduled while the list is non-empty, cancelled when it is empty - `MainApplication.OnCreate` attaches once per process and the Support hook `WatchedLines.Changed` (raised by every successful `Toggle`) keeps it in step. The worker (`WatchedLinesWorker`) re-uses `WatchedLines.CheckAsync` per provider through the widgets' `ProviderRegistry.Override` scope (services via `IPlatformApplication`, the widget precedent; failures retry through WorkManager's backoff) and posts one notification per changed fingerprint - only `Changed` lines, never the `FirstSeen` baseline - on the channel `watched-lines` (`WatchedLineNotification`, id 7316, beside the tracking channels; a new change replaces the one before it). The notification's tap is the replan precedent: an explicit VIEW intent of MainActivity that carries the contract's `ddjourneys://disruptions` link, so the inbox opens the page on a cold start - no state of its own. POST_NOTIFICATIONS (Android 13+) is only requested by the tracking flow; without the grant the worker posts nothing (`Java.Lang.SecurityException` swallowed, like in `LiveJourneyNotification`).
- The platform half, auto-watch during tracking (W1-B4b, `SchutzengelJourneyTracker.CheckWatchedLinesAsync`): the periodic sync (`SyncAsync` with `force: false` only - the loop and the page's `PollAsync`; forced refreshes stay forced) piggybacks `WatchedLines.CheckTrackedAsync` for the live journey's ride lines (`entry.Summary.Lines`), throttled to once per 5 minutes and scoped to the VVO through `ProviderRegistry.Override` (Schutzengel is the DVB/VVO service); the network and the registry come in as two optional constructor arguments (null in the test setup - no auto-watch there). A change adds ONE line to the live notification (`TrackedDisruption`, appended by `SchutzengelLiveContent.Create` while the journey is still going, dropped when it is forgotten): the line becomes part of the content key, so the presentation updates exactly once per change - no notification storm, no second loop.
- The platform half, Windows: no background work (deliberate asymmetry - no scheduler is wired there). The check-on-start is the planner: its `OnAppearing` → `Refresh` → `RefreshWatchedBannerAsync` → `WatchedLineStatus.RefreshAsync` (ten-minute quiet period), and the desktop shell always opens on the planner.
- Line-course diversions (roadmap #17), honest scope: a VVO route change (`rc`) carries a title, free-text description, validity periods and line ids - it names NO stops and carries NO path geometry, so no diversion path is ever drawn and stops are never guessed from free text. What the app can do: `LineDiversions.SkippedStops` - the run window's own stop states mark the stops this run does not serve; the line-course map draws those knots in the cancelled colour with a "not served" popup (`MapScenes.FromLineCourses`), and the active changes of the line ride along as the map page's note (`LineCourseNotices.OfLineAsync`, fetched per map opening, quiet on failure) - shown in the notice card above the map's swipe strip. All three line-course openings carry it (departures line rows, place-search line rows, run page).

## Ride companion (B5, the polish of one ride)
- "Stay in the vehicle" (roadmap #6), detection: `StayInVehicle.After` (Core, pure, unit-tested) - a journey plans a transfer at stop X, and the stop list of the run being ridden also serves the journey's destination AFTER X. Containment by stop id when both sides carry one (ids are authoritative - a different id never falls back to a name match), else by normalized name (spaces and case ignored, the `LineCourseService.SameLine` rule for lines; a PART of a name never matches). The transfer stop must itself be in the run's list - otherwise nothing is claimed. The verdict carries the evidence stop, its index and the arrival time the run's schedule has (omitted when it has none); nothing is guessed. Surfaced on the run page (`RunViewModel.UpdateStayHint`: the followed journey under way whose current ride is THIS run - same line, and the run serves the boarding stop at the ride's own time within 90 s, the `LegRunResolver.Pick` tolerance) and as a hint row under the stops of the current ride in the course strip of the followed journey (the tracked stop list ends at the plan's alighting stop, so the hint there only fires when the Schutzengel service reports the run's stops beyond it - no match, no line).
- "Tight at your pace" (roadmap #6): `JourneyFeasibility.PaceFactor/WalkAtPace/IsTightAtPace` (Core, pure) - the change's quoted walk fits the window, but at the user's walking-pace setting (routing preferences, passed into `TimelineOptions.Pace`) it does not. The factor is the app's own convention (a quarter per pace step, Normal = 1.0): the VVO is sent the chosen pace so its quotes already carry it, the tracking service's walks do not. A pace at or above Normal is never tight; less than half a minute of difference is rounding. Comfortable at the user's pace keeps the old wording - the interchange row only GAINS a `PaceText` line ("Tight at your pace - the walk takes about ...") when the check says tight.
- Get-off alarm (roadmap #9), settings: Settings > Journey options, under the start lead - `AppSettings.GetOffAlarmLeadMinutes` (0/1/2/3, 0 = off, default 1) and `AppSettings.GetOffAlarmSound` (true = alarm). Preferences only, no schema bump (the B3 D-Ticket precedent); the "reset journey settings" button resets them. The alarm itself (`GetOffAlarm` in Core: lead clamp + due decision) is raised by `SchutzengelJourneyTracker.RaiseTransitions` - once per ride, while the journey is riding and the alighting stop is within the lead time - through the two optional ctor args `getOffLeadMinutes`/`getOffAlarmSound` (null in the test setup, the `defaultLeadMinutes` precedent).
- Alert sound, platforms: `JourneyAlert.Gentle` (Core, default false) carries the quiet choice. Android (`LiveJourneyNotification.ShowAlert`): gentle posts on the quiet `live-journey` channel (low importance, no sound) instead of the `journey-alerts` alarm channel; the get-off alert paints the arrival green. Windows (`WindowsLiveJourneySurface`): gentle sets `SuppressDisplay` - the notification lands in the centre without a banner, the honest equivalent of the quiet channel (the builder API has no sound switch; the live notification is muted anyway).
- Stops to go (roadmap #9), notification composition: while riding, the live notification's text gains "N stops to go · exit in about M min" - computed by `RideCountdowns.Of` (Core, pure) from the current episode's stops: the minutes are the run's own schedule (the get-off stop's time), else the remaining stops times the ride's median gap between timed stops, and when the ride carries no time at all only the count is claimed. The line is built in the tracker (`StopsToGoText`, the render pass only - no extra fetch, no second loop) and appended by `SchutzengelLiveContent.Create` BEFORE the B4b disruption line, so the three text lines compose: phase text first, stops-to-go, then the auto-watch's disruption line (both are part of the content key, so the presentation updates when the count drops - `SetOnlyAlertOnce` keeps that silent on Android).
- GPS-corrected marker (roadmap #19), opt-in per followed run: a switch in the "following one run" card of the live vehicles page (`ShowMyPosition`, off for every newly followed run). Foreground only: a 20-second fix loop while the page tracks a run, and ONLY when the `LocationWhenInUse` permission is already granted - the tracking surface never ASKS for it (no prompt; without the grant the switch turns itself off with a hint to allow it in the system settings). NO new permissions were added for this: the manifest keeps its existing location entries (the pre-existing `ACCESS_BACKGROUND_LOCATION` belongs to the widgets' last-known-position path and stays untouched). The fix is snapped onto the stops of the run being ridden by `PositionSnapping.Snap` (Core, pure: projection onto the nearest segment between consecutive stops, clamped to the path's ends) and drawn by `MapScenes.FromTracks` as a "you are probably here" dot (`Extras.YouAreHere`, accent, marker id "you") - only for the first ride still under way, and ONLY while that run's live vehicle marker is missing or older than 90 s (`PositionSnapping.IsFresh`, the vehicles layer's `MaxAge` rule); a fresh vehicle position wins and the dot is not drawn.

## Interfaces, versions and diagnostics
- `InterfaceSchemas` (Core) is the versioned list of every interface the app depends on: external services (VVO WebAPI, TRIAS, Schutzengel, TLMS, open data Dresden, CARTO, the VVO P+R open-data file `vvo-pur`, shared bikes `gbfs`, bike routing `brouter`), internal formats (stored lists, map bridge, plan bridge, widget data, widget cards `widget-card-win`, preferences storage) and the contract. Official versions (TRIAS 1.4, contract 1) are used as they are; for services without a published version the app keeps its own revision `rN` in `InterfaceSchemas.Revision`: raise it whenever a DTO, a mapping rule or a stored/wire format changes. Endpoints live there as constants (`VvoWebApiUrl` ...) and the clients use them. `AppInterfaces` (app) adds the storage schema, the followed-endpoints list (`tracking.endpoints` r1), the watched-line lists (`watched-lines` r1, `watched-line-state` r1 - the second is bookkeeping, never passenger data) and the last departure boards (`board-cache` r1); `Report()` is shown under Settings > Developer options > Interface versions (copyable) and is written at the top of the log (`DiagnosticLog.StartInfo`). New external API, stored format or contract change = update the list and the tests. The three localization files (`IUiStrings`, `EnglishUiStrings`, `GermanUiStrings`) are Compile-Included in the test project, so string wording is unit-tested — and a missing comma between two entries cannot ship again (B5's `ShowMyPositionHint` lost its comma; caught and fixed when the files were first compiled outside the MAUI head, in B7).
- Contract requests are logged as `[Contract vN] ...` (accepted, refused with code, dropped as double delivery).
- `StartupGuard`: `Begin()` first in `App.StartUi()` (the first `CreateWindow`, not in `MauiProgram`: a widget or notification start never builds the UI and must not count as a start), `Complete()` 3 s after the first navigation. Two unfinished starts in a row make a safe start (saved window position forgotten, quick-action publishing skipped, tracking resume delayed 20 s). Keep first-screen work minimal; defer the rest.

- No `Debug.WriteLine`, no always-on files. ## Conventions
- Style classes: Card, Chip, ChipButton, Caption, Faint, Section, Subtitle, Title, Tonal, Divider, ChipLabel. A tappable ChipButton carries `support:Motion.Feedback` (not on chips with a `TouchBehavior`: two touch listeners on one Android view). A divider that precedes a conditional row binds the row's `IsVisible`; list templates draw no divider after their last row (`ShowDivider`).
- Density and text-size tokens (`Space*`, `Pad*`, `Font*`) are rewritten at runtime: XAML reads them as `DynamicResource`, never `StaticResource`.
- Stop sheets go through `Support/StopActions` (ask, then run: departures, journey to/from, share); JSON for page calls through `WebBridge.Json`.
- Accessibility on Android: never `SemanticProperties.Description` on an `Entry` (TalkBack then reads it instead of the text); use the placeholder and `SemanticProperties.Hint`. Helpers: `support:Dense.MinHeight/Padding`, `support:Motion.Feedback`, `support:Themed.*`.
- Icons: vector `Icon`/`IconButton`/`IconGlyph` on a 24x24 grid (add paths in `IconGlyph.cs`). A Button cannot render them; use a tappable Border plus Icon.
- Pills only for non-interactive elements; interactive elements (pickers, tappable chips) are never pills. Native date/time pickers never inside pill chips.
- Accessibility: `SystemAccessibility` (OS text scale, remove-animations, high contrast, screen reader) feeds `Motion.Enabled`, `Dense` (min sizes scale with text), `Icon` size and the map page (font scale). Icons are decorative (not in the accessible tree); the control holding one carries the `SemanticProperties.Description`. `Title`/`Section` labels are headings.
- Bookmarks: `RouteBookmark` (planner, results page header) toggles a saved route; never disabled. The journey page header has no bookmark: its icons are technical details (`TertiaryGlyph`, only while the expert view is on), share (`Secondary`) and refresh (`Action`, right-most like on the results page).
- Native entry frames: our card draws the only contour. Windows: the WinUI text box frame is removed (`Platforms/Windows/NativeStyling`). Android: see "Lessons" (Material 3 text layout, `NativeStyling.Watch`).
- Themes: Light, Dark, Dark AMOLED, System (system dark = AMOLED). Palette keys via `Theme.ColorOf("Bg"|"Surface"|"Raised"|"Outline"|"Ink"|"InkMuted"|"Accent"...)`.
- Localization: `IUiStrings` + `EnglishUiStrings` + `GermanUiStrings` + `CzechUiStrings` (B11; all four compiled into the test project, a completeness test walks the key graph), accessed via `{localization:Tr Group.Key}`. New strings must exist in all four.
- Start, stop-over and destination in headers, card endpoints and the planner/departures stop rows are one line that scrolls sideways (`StopNameView SingleLine="True"`, `RouteView`), never wrapped mid-word; on Android the scroller keeps taps from the row, so pages forward `StopNameView.Tapped` (`JourneyCard.EndpointTapped`).
- Date and time: `WhenPicker` = a strip of day chips (today, tomorrow, five more) + native date and time pickers in a wrapping FlexLayout; no size-driven restructuring.
- Wrapping rows: `FlexLayout Wrap="Wrap" AlignContent="Start" AlignItems="Start"` (the default Stretch makes wrapped rows taller). FlexLayout has no ColumnSpacing; use item Margin.
- Safe area (MAUI docs): ContentPage defaults to None; Layout defaults to Container; ContentView and Border default to None.
- ViewModels: `ObservableObject`, `DisposableViewModel`, `AsyncCommand`/`AsyncCommand<T>`, `PageTeardown`, `Motion.Prepare/EnterPage`, `DiagnosticLog`.
- Theme colours never go into Triggers, DataTriggers or VisualStates (an unapplied setter drops the only DynamicResource registration); use `support:Themed` (Background/OnBackground/IsOn). In C#, switch with `SetDynamicResource` to another token (e.g. `Clear`), never `RemoveDynamicResource`.
- Threading: HybridWebView raw messages and events arrive on a background thread. Always `Dispatcher.Dispatch` before touching views (crash seen in `DisruptionPage.OnLinkTapped`, fixed).

## VVO API facts
- A partial route with `Mot.Type == "Footpath"` is a transfer without stops; `StayForConnection` is an ensured connection (shown as a message, not a real change); `Mobility*` is accessibility.
- Walk-only trips have only transfers, so the mapper builds a synthetic `TransitMode.Walk` leg (`VvoJourneyMapper.WalkOnly`).
- `Journey.Origin/Destination` come from the searched Location (centre point); `leg.From/To` carry platform-level coordinates (GK4→WGS84). Map start/end markers use `MapScenes.Terminal` to prefer the leg position when it is the same stop.
- Timeline: `TimelineBuilder` yields Ride/Walk/Boundary items; `TimelineRows` renders them. An interchange node is merged only when both legs use the same stop (`SameStation`). A change that walks to another stop renders alight → walk → board.

## Offline: city tiles (B7)
- City tiles (`CityTiles`, Core, pure, unit-tested): the offline city map is a FIXED box — lat 51.00–51.11, lon 13.63–13.85 (Dresden and its close outskirts, the map's default centre inside it) — at zooms 10–15, 469 tiles. 15 is the deepest KEPT level: street-detail sharp on a 256 px tile, and every level deeper roughly quadruples the count (z16 alone would add about 1300); the engine's own cap of 19 exists for reading a map, not storing one — deeper levels keep coming live from the network. The honest estimate shown before the download is the count times `BytesPerTile` (a 20 KB average, said as one number; the real size is measured after the download — about 9 MB for today's set; the plan's "~15–25 MB" predates the fixed box).
- `CityTilesStore` (Support, app): `Cache/city-tiles/{z}/{x}/{y}.png`, plain 256 px tiles — no retina doubling (one tile per address whatever screen asks; the page's dark mode inverts by CSS, the cached bytes stay the same light tiles). The download runs only on the button press (Settings, Offline; the OSM tile usage policy — light use), two requests at a time (`AtATime`), shallow levels first, PNG magic bytes decide (a 200 answer that is not a PNG is not a tile), `.part` then move. Source ladder per run: OSM first, CARTO raster (`rastertiles/voyager`, the page's own light source; needs the key) after 8 straight failures; without a key the run stays with OSM and counts its failures. A failed tile is counted, never thrown — the map shows what arrived. `TidyAsync` holds the 60 MB `MaxCacheBytes` (about three honest downloads, next to the plan cache's 160 MB) by deleting the deepest zoom levels first: the overview survives, the sharpest detail is what a later download refetches. The unmetered gate (`AppSettings.CityTilesWifiOnly`, default on) is the RemotePlanTiles rule: `NetworkAccess.Internet` plus a Wi-Fi/Ethernet profile; a metered connection skips the run with an honest status line.
- Offline serving (map bridge r6, additive): the Leaflet engine asks only AFTER a network tile fails — `tileerror` sends the raw message `tile:{z}/{x}/{y}` (once per tile per layer, the page's `tileAsks`); the online path never pays a bridge round-trip. `MapView.ServeTileAsync` answers `ddMapCall('tile', {z, x, y, data})`, `data` = a data: URL of the cached bytes or null (a miss shows Leaflet's own error tile as today). Only tiles of the set are answered (`CityTiles.Within`): outside the city or deeper than 15 the map gets its own miss, never a stretched or stale picture. A served tile shows the honest note (`labels.offlineTile`, `Extras.MapOfflineTiles`, carried by init), which hides again once a network tile arrives.
- Vector engine honesty: the prefetch serves the raster/Leaflet engine only — a device on the MapLibre vector engine gets no offline basemap from this (vector tile download stays parked, a second tile engine). The settings text and the offline note say what is true.
- The downloads call tile.openstreetmap.org and basemaps.cartocdn.com — the same public hosts the page's attribution already names; README and LIESMICH disclose it.

## Sharing
- Provider notices are never part of a share. The model also carries the preferred price (figures line) and guaranteed connections (`IsGuaranteed`, "✓ guaranteed").
- `JourneyShareModel` is the single source for `JourneyShareText` and `JourneyShareImage` (SkiaSharp, drawn in two passes: measure, paint). - Sharing a stop (B8): `StopShare` (Core, pure, unit-tested) composes the payload from the stop itself — the board link exactly as `ContractLinks.Departures` builds it (the name without its city plus the provider-qualified stop key, so the link still resolves when the recipient's app stands on another provider), and a `geo:lat,lon?q=name` link (six decimals, URL-encoded name) — the interchange form of `docs/EXTERNAL_CONTRACT.md` §8, which the app's own `ContractIntents.FromGeo` parses back (tested). A stop without coordinates shares no geo link and no QR code; nothing is invented. No schema bump: nothing stored, nothing on the wire.
- `StopSharePopup` (the `JourneySharePopup` pattern; `StopSharePopup.ShowAsync(page, stop)` is the ONE entry, used by all three stop surfaces: the map stop sheet, the share icon in the departures stop row, the zone plan stop sheet — whose stops carry no coordinates, so there the share honestly comes without a code) shows the stop's name, the QR (`QrCode.Encode`, level M; `StopShareImage` draws black on white regardless of theme, whole-pixel modules around 720 px, the four-module quiet zone already inside the matrix), the share text (`StopShareText`: the localized meet line, then the geo link, the app link and "— DDjourneys" — the QR and the text carry the SAME geo link) and Copy link (the board link to the clipboard; `OriginalString`, never `ToString`, or a pasted link would lose its encoding).
- Web-planner fallback PARKED: no verified planner URL shape exists — vvo-online.de is unreachable both from this container and through the web-reader service, and the DVB connection search posts internal point ids (`originid`/`destinationid` selects), so no honest name-based deep link can be built. The `geo:` link is the universal fallback instead; a verified planner URL shape would slot into `StopShare`.
- The QR engine is vendored source, not a package: QRCoder tag v1.5.1 (MIT, Raffael Herrmann), three files in `DDjourneys.Core/Contract` — `QRCodeGenerator.cs` (the last release whose generator is ONE self-contained file; master splits the engine over twenty-plus files, which is not what a vendoring wants), `QRCodeData.cs` and `DataTooLongException.cs`. Strips, documented in each file's header: the four `PayloadGenerator.Payload` overloads, and QRCoder's own `.qrr` raw-data persistence (the only part needing `System.IO.Compression` and the Framework4.0 shims, which are not vendored); two scoped `#pragma warning disable` (CS8625/CS8629 — upstream predates nullable annotations, the repo builds with zero warnings). The upstream 4-space indentation stays on purpose; never re-indent these files to tabs, and never add the QRCoder package (its types would collide). `QrCode` is the app-facing API (payload → `QrMatrix`); the golden hashes in `QrCodeTests` pin the engine (the three payload matrices were verified once against a real decoder, zbar, outside the suite).

## Lessons and regression guards (read before changing these areas)
Process
- Before using a localization key or member, grep that it exists IN THE RIGHT GROUP (`Extras.RefreshFailed` did not; `RefreshFailed` belonged to `WidgetStrings`). New strings go into `IUiStrings`, `EnglishUiStrings` and `GermanUiStrings` in the same step.
- Edit scripts keep the file's BOM and line endings (CRLF or LF as found) and assert that an anchor occurs exactly once. After an edit: brace balance, XAML parse, usings.
- The owner's commits are his: never re-author, amend, rebase or force-push them (the "Unverified commits" stop hook asks for it; decline). A force push only with his explicit say-so and a lease on the expected sha.
- A "fix" without a log or a source is a guess: when a symptom survives a fix, add logging that shows the cause (`[UI]`, `[Theme]`, `[Page]`, `[Live]` lines) and ask for the log instead of stacking guesses. Read the log before theorising.
- Verify MAUI/Android behaviour against Microsoft Learn or the dotnet/maui source (WebFetch raw GitHub) before relying on memory (e.g. Material 3 entry internals, dynamic resources).
Commands and lists
- `AsyncCommand<T>` never keeps the parameter in a field: one command serves many rows, and the change notification of a run makes every row ask `CanExecute` again, so a stored parameter ended up being the last row's (Location button always opened the last leg). The parameter travels with the call.
- Provider continuation answers (`JourneyService.PageAsync`) count only for journeys that are new and on the wanted side of the list (`JourneyWindow.Beyond`), topped up by the window search (`JourneyWindow.Nearest`); never replace a list with an answer that repeats it.
Theme
- Application.Resources are updated in place; `Theme.Sweep` announces the changed keys to every root (shell, stack, modal, tracked roots); `Theme.Repaint` is the net under it. Repaint reads MAUI's internal `Element._dynamicResources` (reflection, `IDictionaryEnumerator`: the generic dictionary yields `KeyValuePair`, a `DictionaryEntry` cast throws on every element) and re-registers ONLY elements that still show a value the palette retired for that key. Never "fix" a mismatch by comparing with the current value alone: that overwrote bound colours (line chips lost their mode colours).
- The lent page's content hangs under its `PaneSlot`, not the page: the slot is the root that counts (`Theme.Track`). Density has the same weakness (`Density.Revalidate` is per page); fix it the same way if it shows.
- Line chips: `ModeChips.For(mode)` fill/shape/stroke come from a binding (`Look`), the `Chip` style supplies size and padding. Followed journeys use them too (`LinePart.Look`, `ModeChips.Marked` outlines the ride under way, `ModeGuess.OfLine` when only a name is known).
- Mica = calm (more of the palette, less accent), Mica Alt = pronounced (thinner tint, more accent); small steps in `MaterialProfile.Look`, tested in `MaterialProfileTests`.
Android
- Release builds run R8 and it removes every class that only a manifest names: crashes at start were `androidx.startup.InitializationProvider`, then `androidx.core.app.CoreComponentFactory`. `Platforms/Android/ProGuard.cfg` keeps all of `androidx.**` plus the manifest component kinds; add keep rules there, never one crash at a time (the library manifests' keep rules do not reach R8 in this build). The `.csproj` R8/d8/multidex properties are global for Android.
- With `UseMaterial3` the Entry's native view IS a `MauiMaterialTextInputLayout` (outlined box). Its EditText keeps the box drawable as background even after `BoxBackgroundMode = None`; the handler mappers can run before Material applies the outline. So `NativeStyling.Watch(activity)` (called in `MainActivity.OnResume`) sweeps the window after every layout pass: layout box mode/stroke/background and the EditText background are cleared, only when something is left (no layout loops). Dialog and popup windows are not covered. Editors and pickers get the same clean-up.
- Caret, drop and selection handles/highlight wear the palette Accent (`NativeStyling.Tint`, Android 10+ only, drawables are copies of the shared system ones, new colour appears when the caret/handle is drawn again); `Theme.Changed` sweeps at once.
- A horizontal `ScrollView` keeps taps from its parent on Android: forward them (legs row of `JourneyCard`, `StopNameView.Tapped`, `EndpointTapped`).
